- **架构模式**: Next.js 14 App Router with Server Components
- **性能要求**: 页面首次加载时间 < 1.5秒，服务端渲染优化
- **数据获取**: 直接使用Prisma查询，避免额外API调用

1. **页面重构**: 将现有dashboard从用户信息展示转换为工作台卡片列表
2. **数据展示**: 显示用户的所有分析卡片，包含源标题、版本标题、创建时间

- **边界条件**: 处理用户无卡片、卡片数据不完整等边界情况

## 🚨 重要注意事项 (Important Notes)

### 技术风险
- **数据查询复杂性**: User -> AnalysisSource -> AnalysisCard的三层关联查询可能影响性能
- **现有页面重构**: 需要确保不破坏现有的认证和布局功能
- **类型安全**: Prisma查询结果的类型与前端展示类型需要精确匹配

### 最佳实践
- 使用Next.js Server Component进行服务端渲染，提升性能
- 合理使用Loading和Error Boundary处理各种状态
- 保持组件的单一职责，便于测试和维护

### 常见Bug预防 (基于项目经验)

#### 1. 数据查询错误预防
- ❌ **错误做法**: 假设AnalysisCard表有userId字段直接查询
- ✅ **正确做法**: 通过User -> AnalysisSource -> AnalysisCard关联查询

#### 2. 类型定义不一致预防
- ❌ **错误做法**: 组件期望string类型的createdAt，实际是Date类型
- ✅ **正确做法**: 明确定义接口类型，确保组件使用的数据类型一致

#### 3. 空状态处理遗漏预防
- ❌ **错误做法**: 只考虑有数据的情况，忽略空数组的处理
- ✅ **正确做法**: 先实现空状态组件，再实现数据展示组件

#### 4. 导航更新遗漏预防
- ❌ **错误做法**: 只更新页面内容，忘记更新导航链接文案
- ✅ **正确做法**: 在checklist中明确包含导航组件的更新要求
