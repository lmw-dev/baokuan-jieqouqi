# 文档体系设计指南

> **核心理念**: 先设计方案，再执行实现，最后管理协作

---

## 📋 概述 (Overview)

本文档体系基于**独立开发**和**vibe coding**模式设计，通过三个文档规则实现从需求到交付的完整流程：

- **🎯 Dev文档**: 技术设计和方案规划
- **🤖 Prompt文档**: AI执行指令和实现要求  
- **👥 Task文档**: 人机协作管理和验收协调

---

## 📚 三大文档规则详解

### 🎯 Dev文档 - 技术设计规划

**文件位置**: `.cursor/rules/230-wf-write-dev-docs.mdc`
**输出路径**: `docs/development/[Task-ID]-dev-[title].md`

#### 核心定位
- **阶段**: 设计阶段（接收Linear Issue后的第一步）
- **职责**: 技术方案设计、架构规划、实现路径分析
- **输出**: 为Prompt文档提供技术设计基础
- **用时**: 30-60分钟深度技术分析

#### 主要内容
1. **🎯 设计概述**
   - 设计目标和技术范围
   - 核心设计决策和原则
   - 设计输出和交付物

2. **🏗️ 技术架构**
   - 技术栈选择和理由
   - 架构模式和设计模式
   - 组件关系和接口定义

3. **📋 实现规划**
   - 具体实现步骤
   - 开发里程碑
   - 风险评估和应对策略

4. **🔧 质量标准**
   - 代码质量要求
   - 性能基准
   - 测试覆盖标准

#### 关键特点
- ✅ **设计导向**: 专注于技术方案设计，不是实现记录
- ✅ **架构重点**: 强调系统架构和技术选择
- ✅ **基础作用**: 为Prompt文档提供技术设计基础
- ✅ **风险意识**: 前置风险分析和应对策略

---

### 🤖 Prompt文档 - AI执行指令

**文件位置**: `.cursor/rules/250-wf-prompt-engineering.mdc`
**输出路径**: `docs/prompts/[Task-ID].prompt.[title].md`

#### 核心定位
- **阶段**: 执行阶段（基于Dev文档生成AI指令）
- **职责**: 将技术设计转化为AI可执行的具体指令
- **输出**: 确保AI准确理解和执行技术方案
- **用时**: 20-30分钟指令编写

#### 主要内容
1. **🎯 目标定义**
   - 基于Dev文档的执行目标
   - 明确的验收标准
   - 具体的成功指标

2. **📋 上下文引用**
   - 关键文件的@引用路径
   - 依赖服务的接口验证
   - 现有代码的调用示例

3. **🔧 实现要求**
   - 具体的技术约束
   - 详细的代码结构
   - 类型定义和接口规范

4. **🔄 执行步骤**
   - 分阶段的实现步骤
   - 优先级和依赖关系
   - 检查清单和验证点

#### 关键特点
- ✅ **执行导向**: 专注于AI的具体执行指令
- ✅ **上下文完整**: 提供充分的代码上下文和引用
- ✅ **步骤明确**: 详细的实现步骤和验证标准
- ✅ **质量保证**: 完整的检查清单和错误预防

---

### 👥 Task文档 - 人机协作管理

**文件位置**: `.cursor/rules/231-wf-write-task-docs.mdc`
**输出路径**: `docs/tasks/[Task-ID]-task-[title].md`

#### 核心定位
- **阶段**: 产品规划阶段（基于Linear Issue直接生成）
- **职责**: 从产品角度确定人机分工、验收标准、进度管理
- **输出**: 为整个项目提供协作框架和验收基准
- **用时**: 5-10分钟快速决策

#### 主要内容
1. **🎯 快速决策摘要**
   - 业务优先级和核心价值
   - 技术方案和时间预估
   - 主要风险和应对策略

2. **🔑 人机分工清单**
   - 人类负责的战略决策
   - AI负责的执行任务
   - 明确的协作界限

3. **📦 AI指令包**
   - 简洁的执行目标
   - 关键的技术约束
   - 明确的验收标准

4. **📈 执行记录**
   - 时间和进度记录
   - 关键决策记录
   - 完成确认清单

#### 关键特点
- ✅ **轻量级**: 5-10分钟完成，适合独立开发
- ✅ **分工明确**: 清晰的人机协作界限
- ✅ **管理导向**: 专注于协作和进度管理
- ✅ **决策支持**: 快速的业务和技术决策

## 🚀 使用指南 (Usage Guide)

### 📋 标准流程

1. **📥 接收Linear Issue**
   - 理解业务需求和验收标准
   - 识别技术挑战和关键风险

2. **🎯 创建Dev文档 + 👥 创建Task文档（并行）**
   ```bash
   # 基于Linear Issue创建技术设计文档
   AI: 根据@Linear-Issue-Link 创建 [Task-ID]-dev-[title].md
   
   # 基于Linear Issue创建人机协作管理文档
   AI: 根据@Linear-Issue-Link 创建 [Task-ID]-task-[title].md
   ```
   
   **Dev文档**:
   - 完成技术方案设计
   - 确定架构和实现路径
   - 评估风险和制定应对策略
   
   **Task文档**:
   - 明确人机分工界限
   - 设定协作和验收标准
   - 建立进度跟踪机制

3. **🤖 生成Prompt文档**
   ```bash
   # 基于Dev文档和Task文档生成AI执行指令
   AI: 根据@[Task-ID]-dev-[title].md 和@[Task-ID]-task-[title].md 创建 [Task-ID].prompt.[title].md
   ```
   - 将技术设计转化为AI指令
   - 结合Task文档的验收标准
   - 确保指令的完整性和准确性

4. **⚡ AI执行实现**
   ```bash
   # 基于Prompt文档执行实现
   AI: 根据@[Task-ID].prompt.[title].md 执行技术实现
   ```
   - 按照Prompt指令执行代码实现
   - 遵循Dev文档的技术设计
   - 完成Task文档的验收标准

### ⚠️ 注意事项

1. **文档依赖关系**
   - Linear Issue → Dev文档（技术设计）+ Task文档（协作管理）
   - Dev文档 + Task文档 → Prompt文档（执行指令）
   - Task文档和Dev文档是并行创建的，都基于Linear Issue

2. **职责边界**
   - Dev文档：技术设计，不涉及具体实现
   - Prompt文档：执行指令，不涉及技术决策
   - Task文档：协作管理，不涉及技术细节

3. **质量保证**
   - 每个文档都有明确的检查清单
   - 确保文档间的一致性和连贯性
   - 定期回顾和优化文档质量

## 💡 最佳实践 (Best Practices)

### 🎯 Dev文档最佳实践

1. **技术决策记录**
   - 记录为什么选择某种技术方案
   - 分析不同方案的优缺点
   - 考虑未来的扩展性和维护性

2. **架构设计原则**
   - 保持架构的简洁性和可理解性
   - 考虑系统的可测试性和可维护性
   - 预留未来功能扩展的接口

3. **风险评估方法**
   - 识别技术风险、性能风险、集成风险
   - 为每个风险制定具体的应对策略
   - 考虑风险的概率和影响程度

### 🤖 Prompt文档最佳实践

1. **上下文引用规范**
   - 使用@符号引用具体文件路径
   - 验证所有依赖服务的接口
   - 提供充分的代码示例和说明

2. **指令明确性**
   - 使用具体的技术术语
   - 避免模糊的表述和要求
   - 提供可测试的验收标准

3. **错误预防机制**
   - 基于历史经验预防常见错误
   - 添加接口依赖检查清单
   - 强调类型安全和边界条件

### 👥 Task文档最佳实践

1. **快速决策支持**
   - 专注于必须由人类做的决策
   - 避免技术细节的重复描述
   - 保持文档的轻量级和高效性

2. **人机分工明确**
   - 清晰定义人类和AI的职责边界
   - 避免职责重叠和模糊地带
   - 建立有效的协作机制

3. **进度管理有效**
   - 设定明确的里程碑和检查点
   - 建立问题上报和解决机制
   - 保持项目进度的可视化
